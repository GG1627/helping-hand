\subsection{Findings and effect on beta strategy}
Recorded limitations include a glove that had been disassembled and not revalidated in its current assembly, a firmware startup wait tied to serial readiness, unmeasured phone-side BLE loss under sustained use, unknown exact IMU identity/magnetometer capability, and no real multi-signer word-model evaluation. These are documented risks, not asserted alpha test failures. The repository does not tie specific UI changes to measured participant feedback.

Beta work adds email/password account flows, UID-scoped local progress, separate practice routes, and route-level live state updates while retaining the static 36-class baseline. The beta plan therefore prioritizes boot without a serial host; current-assembly sensor/BLE checks; Back, retry, and stale-state transitions; account isolation and sync; recording/export integrity; and independent usability. Word practice pages are accessible UI; dynamic recognition and word completion are not yet integrated.

\section{Expected Behavior}
\subsection{System operation}
The glove samples five flex channels and six accelerometer/gyroscope channels on a Feather ESP32-S3. Firmware targets 40 Hz and transmits timestamped, sequenced sensor and static prediction data over BLE. Flutter displays connection and prediction state, permits static letter/number practice, records labeled sensor trials, and stores progress locally under the signed-in Firebase UID with asynchronous Firestore synchronization. Dynamic word recognition is a beta goal; it must not be represented as available until a real-data-trained model passes the gates in Test ML-02.

\section{Test Procedures}
\subsection{Execution and evidence rules}
The reference configuration is branch \code{gael}, source commit \code{14f7aad}, Flutter package \code{1.0.0+1}, Adafruit Feather ESP32-S3, and the T1 reference phone Fairphone Gen 6 / Android 15. Record the actual app artifact, phone/OS, firmware, IMU marking, power source, date, tester, and reviewer for every run; deviations from the reference configuration are permitted but must be stated. Firebase project ID is \code{helping-hand-83137}; use test accounts or the Firebase emulator, never change production rules as part of a test.

Every procedure below is \status{}; older unit/build evidence is not a pass for a new beta route or physical setup. Use pseudonymous participant IDs, obtain required consent before recording people, and retain original data. For each run record the test ID, numbered attempt, measured values, Pass/Fail/Blocked/Not run, defect and retest commit, and evidence filenames. A case blocked by missing physical hardware, consent, reviewer, or trained model is recorded as Blocked with its reason.

\subsection{Run record and exit decision}
For every attempt, retain one row with test ID/run, date/time, tester/reviewer, commit and artifact hash, phone/OS, board/IMU/firmware/source, Firebase environment, measured values, status, defect/retest link, and evidence filenames. Never store passwords or direct participant identifiers in logs. Do not modify criteria after seeing results without versioning the plan and recording the rationale.

The beta is not fully validated until hardware/stream, navigation/live route, authentication/isolation, offline/sync, recording/export, outside-user accessibility/usability, and dynamic word model/integration cases have recorded results. Any unmet model gate is reported as a measured limitation; keep the static baseline. A no-model result is not recast as a successful word test. Resolve the existing static-completion-after-Back behavior before final release assessment.
